# iced + Vite template

A starting point for building [iced](https://iced.rs) 0.14 apps with **Vite**
and **Rust → WebAssembly**, with no Trunk in the loop.

The template is three things: a minimal counter app, a Vite dev loop that
rebuilds and reloads the WASM on every Rust change, and an in-house Vite plugin
that owns the whole `wasm-pack` invocation.

## What makes this different from `trunk`

`trunk` shells out to `wasm-bindgen` on its own schedule and serves its own HTML.
Vite owns the page, so the WASM build becomes an ordinary module that HMR, code
splitting, and the rest of the toolchain treat like any other dependency. If you
already have a TypeScript codebase, this drops in without giving up `vite dev`.

## Requirements

| Tool        | Version                                    | Why                                            |
| ----------- | ------------------------------------------ | ---------------------------------------------- |
| **Nightly** | `rustup default nightly`                   | `[unstable] build-std` in `.cargo/config.toml` |
| wasm target | `rustup target add wasm32-unknown-unknown` | Build target                                   |
| `wasm-pack` | `cargo-binstall wasm-pack`                 | The build driver the plugin invokes            |
| Bun         | any recent                                 | Installs workspaces and runs the scripts       |

> **Nightly is required, not optional.**
> `.cargo/config.toml` sets `build-std = ["std", "panic_abort"]` and
> `panic-immediate-abort = true`, which are nightly-only. Stable Rust will
> refuse to build this template.

## Getting started

```bash
bun install
rustup default nightly
rustup target add wasm32-unknown-unknown
cargo-binstall wasm-pack

bun run dev
```

Open the printed URL. The counter increments, and a Rust change triggers a
rebuild and reload with no second terminal and no `cargo-watch`.

## Scripts

| Script                 | Does                                               |
| ---------------------- | -------------------------------------------------- |
| `bun run dev`          | Web dev server; builds WASM, watches Rust, reloads |
| `bun run build`        | Release WASM + production bundle into `dist/`      |
| `bun run preview`      | Serves the built `dist/` output                    |
| `bun run dev:native`   | Runs the desktop binary (`--features native`)      |
| `bun run build:native` | Desktop release build                              |
| `bun run dev:docs`     | Runs the [iced docs](docs/) site in watch mode     |
| `bun run typecheck`    | Typechecks the plugin                              |

## Layout

```text
.
├── Cargo.toml            # crate `app`, cdylib + rlib
├── .cargo/config.toml    # wasm target, build-std, panic settings
├── src/
│   ├── lib.rs            # Counter app; #[wasm_bindgen(start)] boots the web
│   └── main.rs           # desktop entry point, `--features native`
├── main.ts               # imports build/app.js and calls init()
├── index.html
├── vite.config.ts        # plugins: [wasmPack()]
├── build/                # ← generated by wasm-pack, never edit
├── docs/                 # iced 0.14 guide (VitePress)
└── packages/
    └── vite-plugin-wasm-pack/   # the plugin — see its own README
```

`build/` is the plugin's default `outDir` and never collides with Vite's own
`dist/` bundle.

## Configuration

```ts
import { defineConfig } from "vite";
import wasmPack from "vite-plugin-wasm-pack";

export default defineConfig({
  plugins: [wasmPack()],
});
```

Every option is a default: the crate is the Vite root, `wasm-pack` targets
`web`, the output name falls back to the crate name, and the output lands in
`build/`. For anything beyond that — non-default `outDir`, a crate in a
subdirectory, path dependencies, cargo passthrough flags — see the
[plugin's own README](packages/vite-plugin-wasm-pack/README.md), which documents
every option and the two-argument-space problem that trips people up.

## Web and native are separate feature flags

The two targets need different backends, so each carries its own. `wasm` is the
default, so the web path needs no flags at all.

| Feature  | Renderer             | Windowing             | Trigger with         |
| -------- | -------------------- | --------------------- | -------------------- |
| `wasm`   | `wgpu` + `webgl`     | none — winit not used | `bun run dev`        |
| `native` | `tiny-skia` + `wgpu` | `x11`, `wayland`      | `bun run dev:native` |

```bash
bun run dev             # web, via Vite
bun run build           # web, production bundle
bun run dev:native      # desktop window
bun run build:native    # desktop, optimised
```

> **The native commands pass `--no-default-features`.** Without it the default
> `wasm` feature rides along and drags the web bindings into the desktop build.
> The two entry points are `#[cfg]`-gated, so nothing breaks — you just carry
> `web-sys` baggage you do not need.

## Native gets its own profile

`release` is the shared base: it is what both shipping builds inherit from. Each
target then overrides what it cares about. The browser cares about bytes, since
the `.wasm` is downloaded; a desktop binary is local, so the startup time is
what the user feels:

```toml
# shared base
[profile.release]
codegen-units = 1
opt-level = 3

# browser: small, because it is downloaded
[profile.wasm-release]
inherits = "release"
opt-level = "s"
strip = "debuginfo"

# desktop: fast, because it is already on disk
[profile.native-release]
inherits = "release"
lto = true
strip = false
```

| Setting   | `wasm-release` | `native-release` | Why                                    |
| --------- | -------------- | ---------------- | -------------------------------------- |
| opt       | `s`            | `3`              | Optimise for size vs. for speed        |
| debuginfo | stripped       | kept             | Useful stack traces from a local crash |
| LTO       | off            | full             | Cross-crate inlining, at the cost of a |
|           |                |                  | slower build                           |

The `release-` prefix is what lets both profiles inherit from `release` in the
same file. A custom profile may only inherit from `release`, `dev`, or a profile
it already extends, so naming them `wasm` and `native` would have forced
`inherits = "release"` with no `release-` grouping to read as a family.
